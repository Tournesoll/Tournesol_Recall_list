# Recall Lite 升级开发总要求

## 1. 目标与冻结范围

本轮只实现以下五类升级，不扩展为在线学习平台：

1. UI 与移动端适配：改善外观、触控和响应式布局，消除长文本造成的横向溢出。
2. MiMo v2.5 AI：应用直接调用，支持 AI 卡片导入、背诵中临时答疑、记录页近期学习分析。
3. 题目解析与笔记：统一称为“题目解析”，与笔记放在同一个“详细介绍”区域中切换。
4. 背诵多任务：IndexedDB 保存，最多 3 个未完成任务，支持暂停、继续、新建、删除和完成历史。
5. 文档与 Android 交付：维护开发过程资料，最终由项目负责人完成合并和 APK 验证。

明确不做：账号、云同步、后端代理、长期 AI 对话、答疑记录、AI 生成笔记、Word/PDF 导入、OCR 服务、在线题库。

## 2. 已确认的产品规则

### AI 配置

- 模型使用小米 MiMo v2.5，由应用直接请求。
- API Key 由用户在设置页填写，只保存在本机，不得写入源代码、示例、日志或 Git。
- AI 请求代码必须集中管理，AI 导入、答疑和学习分析不得各自复制一套请求逻辑。
- 必须有超时、取消、错误文案和重试上限。不得无限重试。
- 开发时只能使用占位符或本机未跟踪配置；PR 截图、日志和开发说明不得出现真实密钥。

### AI 导入

- 输入来源：粘贴文本、图片、多张图片的上限由实现说明固定、`.txt` 文件。
- 暂不支持 Word/PDF。
- 用户提交前必须先选择允许生成的卡片类型，并选择是否生成“题目解析”。
- 沿用 `recall`、`cloze`、`choice` 三种 JSON 卡片类型。
- 生成结果先通过本地结构校验，再进入预览；预览中可编辑、删除，确认后才写入知识库。
- AI 输出失败或 JSON 不合法时允许自动修复，最多 3 次；3 次后停止并向用户展示可操作的错误。
- 当前“复制提示词到外部 AI”方式保留。外部 AI 模式启用解析时，提示词中也必须要求统一的 `explanation` 字段。

### 背诵答疑

- 只有揭晓当前卡片答案后才允许打开“问 AI”。
- 请求上下文只包含当前卡片的必要题目、答案和题目解析，以及用户本次问题。
- 提示词软限制回答当前题目相关问题。
- 回答支持 Markdown 展示。
- 不保存问答、不生成笔记、不跨卡片保留上下文；切换卡片后立即清空问题、回答、加载状态和错误状态。
- 默认按单轮问答实现，不提供长期会话。

### 题目解析与笔记

- 新功能统一使用“题目解析”，不再使用“单词解释/造句/知识点讲解”等分类。
- 回忆卡、填空卡和选择题都允许具有题目解析。
- 每张卡片独立保存解析和笔记，均可手动编辑。
- 背诵页在题目下方提供一个可折叠的“详细介绍”区域。
- 只有解析时显示解析；只有笔记时显示笔记；二者都有时使用“题目解析/笔记”标签切换；二者都没有时不显示。
- 显示还需要支持每张卡片的关闭、答案后显示、始终显示三种状态。旧数据缺少状态字段时必须采用兼容默认值。
- 解析和笔记内容支持 Markdown；不得直接把不可信文本插入 `dangerouslySetInnerHTML`。

### 背诵任务

- 最多 3 个未完成任务；已完成历史不占名额。
- 任务必须保存在 IndexedDB，不能只保存在 `localStorage`。
- 任务至少保存：id、名称、来源筛选摘要、原始条目 id、本轮队列、每条会话状态、完成记录、状态、创建时间、更新时间和完成时间。
- 暂停当前任务后返回任务列表；任务列表允许继续、新建和删除未完成任务。
- 完成后保留历史记录。删除未完成任务必须确认；不删除已经写入的正式复习日志。
- 删除知识库或内容后，继续旧任务时必须过滤不存在的条目并保持页面可用。

### AI 学习分析

- 位于记录页，分析最近 7 天或 30 天，默认 7 天。
- 只提交聚合后的学习数据，不提交整库题目正文。
- 输出学习量、掌握情况、薄弱方向、复习压力和可执行建议，使用 Markdown 展示。
- 分析结果只在当前页面保留，不写入数据库。

## 3. 当前项目事实

- Web：React 18、TypeScript、Vite、HashRouter、普通 CSS。
- 数据：Dexie/IndexedDB；当前数据库版本为 5，共 5 张表。
- Android：原生 Java WebView 壳，不是 Capacitor。
- 当前主要页面、旧代码边界和构建方式见：`项目初始情况/情况说明.md`、`项目初始情况/页面说明.md`。
- `src/App.tsx` 同时包含旧版和 V2 代码。当前入口是文件末尾导出的 `App`；禁止把功能误接入 `LegacyApp`。

## 4. 分工与文件所有权

### 共享合同（已冻结）

- `src/domain.ts`：统一领域类型，包括 `MemoryItem`、`ContentDisplayMode`、`StudyTask`、复习日志和“题目解析”标签。
- `src/contracts.ts`：统一 AI 边界类型，包括导入卡片、当前卡片答疑上下文和 7/30 天分析聚合数据。
- 这两个文件是袁翊博在基线阶段预置的共享合同。开发者必须直接复用，不得各自复制同名 interface；需要调整时先在 Issue 中说明并由袁翊博批准。

| 人员 | 主要职责 | 开发阶段允许修改 |
| --- | --- | --- |
| 袁翊博 | 基线、缺陷、集成、依赖、共享接线、Android | 个人规范中列出的集成文件；其他人开发期间不并行改其独占文件 |
| 候舒扬 | MiMo 客户端、AI 导入、临时答疑、学习分析 | 仅 `src/features/ai/**` 和自己的开发后说明；复用 `src/contracts.ts` |
| 贾源 | UI、长文本适配、详细介绍、多任务 | `src/App.tsx`、`src/db.ts`、`src/styles.css`、`src/v2.css`、`src/features/details/**`、`src/features/study-tasks/**` 和自己的开发后说明；复用 `src/domain.ts` |
| 杨桀浩 | 文档整理和最终开发报告 | `开发报告.md`、自己的开发后说明；代码只读 |

任何人需要越界修改时：停止修改，在开发后说明的“需要负责人接入”中写出文件、目的、建议代码位置和接口。不得以“顺手修复”为理由编辑别人的文件。

## 5. 推荐实施顺序

### 阶段 0：负责人冻结基线

1. 提交或妥善保存当前工作区已有变更。
2. 确认 `npm run build` 成功并记录基线 commit。
3. 创建 GitHub Issue 和分支，确保所有成员从同一 commit 开始。
4. 由负责人统一决定并安装 Markdown 渲染所需依赖；其他成员不得各自修改依赖文件。

### 阶段 1：并行开发

- 候舒扬只新增 AI 模块，使用 props/callback 与页面和数据库解耦。
- 贾源负责当前页面文件、数据库任务表和非 AI 交互，不导入候舒扬尚未合并的实现，可使用明确的占位接口。
- 项目负责人只做评审、Issue 澄清和不冲突的准备工作，避免在此阶段同时修改 `App.tsx`、`db.ts` 和 CSS。
- 杨桀浩可以搭建报告提纲，但不得把未合并功能写成已完成。

### 阶段 2：负责人集成

1. 先合并贾源的 UI/多任务分支。
2. 再合并候舒扬的新增 AI 文件。
3. 由负责人修改共享路由、页面、数据库适配和依赖，将 AI 组件接入。
4. 处理缺陷后执行完整回归。

### 阶段 3：文档和发布

1. 三位开发者补全开发后产出文档。
2. 杨桀浩依据实际合并 commit 和开发后说明完成 `开发报告.md`。
3. 负责人执行 Web 构建、Android 资源同步、APK 构建和真机验收。

## 6. GitHub 规范

- 所有人必须从同一基线 commit 建分支，不从他人的开发中分支继续。
- 建议分支：`feature/ai-mimo`、`feature/ui-study-tasks`、`integration/release`、`docs/development-report`。
- 一个提交只表达一个可说明的变更，禁止“全部修改”“final”等无信息提交名。
- 建议提交格式：`feat(ai): add MiMo import preview`、`fix(ui): wrap long study text`、`docs: update development report`。
- 开发者不得直接向 `main` 推送；通过 PR 合并。
- PR 必须说明：功能范围、修改文件、数据结构变化、验证命令、手工验证、已知问题、负责人需要完成的接线。
- 合并前先同步基线并自行解决仅属于自己文件的冲突；共享文件冲突交给项目负责人。
- 禁止对共享分支强制推送，禁止提交 `node_modules`、`dist`、APK、真实备份和 API Key。

## 7. 编码与界面规范

- 保持严格 TypeScript，避免新增无边界的 `any`；外部 AI 数据必须在边界处校验。
- 复用现有数据类型和组件风格，新增抽象只为清晰的功能边界服务。
- 所有网络请求必须可取消、可超时，并处理离线、401/403、429、5xx、解析失败和用户取消。
- 所有异步按钮必须有加载态并防止重复提交。
- 移动端以 360 px 宽度为最低验收宽度；页面不得产生非预期横向滚动。
- 长中文、长英文、URL、Markdown、代码块和公式都不能撑破父容器。普通文本换行，代码块才允许容器内横向滚动。
- 点击区域不小于 44 px；固定底栏不得遮挡页面内容和输入法区域。
- 图片必须限制类型、数量和大小，生成预览 URL 后及时释放。
- 用户内容渲染必须防止脚本注入。

## 8. 测试与清理规范

每个 PR 至少完成：

1. `npm run build`。
2. 360×800、390×844、768×1024、桌面宽度的关键页面检查。
3. 正常、空数据、长文本、加载、失败、取消和重复点击状态。
4. 涉及 IndexedDB 时验证新库、旧库升级、刷新恢复、删除关联数据。
5. 涉及 AI 时使用脱敏样例验证成功、超时、鉴权失败、限流、非法 JSON、连续 3 次修复失败和取消请求。

本项目当前没有正式测试框架。允许使用临时测试页面、模拟响应、截图和样例文件，但在提交前必须删除临时测试路由、测试账号、测试密钥、模拟开关、调试按钮、日志和样例数据。若负责人批准新增可长期维护的自动化测试，正式测试文件可以保留，不属于临时文件。

## 9. 完成定义

满足以下全部条件才可称为完成：

- 只修改允许的文件。
- 功能符合本文件和个人规范。
- 构建通过，手工验收记录完整。
- 没有真实 API Key、私有学习内容或临时测试产物。
- 自己的 `开发后产出文档/...` 已填写，而非保留模板占位文字。
- PR 中逐项列出修改文件，并标注负责人仍需接入的内容。
