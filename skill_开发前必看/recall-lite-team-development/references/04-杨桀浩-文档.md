# 杨桀浩文档工作规范

## 1. 职责定位

负责依据实际合并代码、PR、测试记录和三位开发者的开发后说明，编写最终 `开发报告.md`。不得根据计划把未完成、未合并或未验证的功能写成已实现。

## 2. 允许修改的文件

```text
开发报告.md
开发后产出文档/杨桀浩/文档工作说明.md
```

其余文件只读。发现代码、文档或测试证据冲突时，向项目负责人提出问题，不自行修改代码或别人的开发说明。

## 3. 必读资料

按以下顺序阅读：

1. `项目初始情况/情况说明.md`
2. `项目初始情况/页面说明.md`
3. `skill_开发前必看/recall-lite-team-development/references/00-总要求.md`
4. `开发后产出文档/候舒扬/开发后说明.md`
5. `开发后产出文档/贾源/开发后说明.md`
6. `开发后产出文档/袁翊博/合并与发布说明.md`
7. GitHub Issues、PR 描述、合并 commit 和最终代码

开发前个人文档用于了解职责，不作为“已经实现”的证据。

## 4. 报告内容要求

最终报告至少包含：

- 项目背景和升级目标。
- 升级前架构与主要功能。
- 团队分工、GitHub 协作和合并顺序。
- UI、AI 导入、背诵答疑、题目解析/笔记、多任务、AI 学习分析的实际实现。
- 技术方案：MiMo 直接调用、本地 Key、JSON 校验/修复、IndexedDB 迁移、Markdown、安全与错误处理。
- 页面变化和用户操作流程。
- 测试环境、用例、结果、APK 构建与真机验证。
- 文件变更摘要、已知限制和后续计划。

每一项必须区分：已完成并验证、已完成未验证、部分完成、未实现。Word/PDF 导入、答疑记录和 AI 生成笔记明确属于本轮不实现范围。

## 5. 证据与写作规范

- 技术结论应能追溯到代码路径、PR、commit 或开发后说明。
- 版本、依赖、数据库版本、路由和 APK 信息以最终合并分支为准。
- 不公开 API Key、Authorization 头、个人学习资料、真实 AI 请求全文。
- 可使用脱敏截图，但需标注页面和测试环境。
- 避免使用“完全解决”“百分百稳定”等没有证据的表述。
- 保留统一术语：“回忆卡、填空卡、选择题、题目解析、笔记、详细介绍、背诵任务、MiMo v2.5”。

## 6. 验收与输出

- 检查报告中所有相对路径和章节索引。
- 与项目负责人核对最终 commit、数据库版本、构建命令、APK 路径和真机结果。
- 列出的测试必须来自真实执行记录。
- 填写 `开发后产出文档/杨桀浩/文档工作说明.md`，记录资料来源、仍缺少的证据和报告完成状态。
